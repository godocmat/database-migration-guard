# PostgreSQL inspection evidence

DMG-10 collection and DMG-11 comparisons use the version 1 types in `dmg_core::inspection`, `dmg_core::snapshot`, and `dmg_core::history`. Keep full catalog artifacts in protected storage. Deparsed expressions can contain sensitive literals, and qualified identifiers can disclose schema design. Keep endpoints, roles, credentials, server messages, and application row values out of these artifacts. `TargetId` is an opaque identifier supplied by the operator. It carries no connection details. [Catalog feasibility and transport evidence](research/postgresql-inspection.md)

## Observation and scope

`InspectionScope` is a nonempty list of up to 32 unique non-system schemas. `InspectionEvidenceV1` records the effective observation of every requested schema. A visible empty schema, a missing schema, denied access, and an unavailable read have distinct states. An attached `SchemaSnapshotV1` includes exactly the visible schema names. An unavailable collection can return observation and gap data without a snapshot. `Observation` carries the target ID, optional numeric server version, and UTC Unix time in whole seconds. The numeric server version covers PostgreSQL 15–18 catalog observations independently of the declared offline parser target.

`CatalogField` distinguishes `observed`, `estimated`, `unavailable`, and `not_applicable`. `RelationEstimates` labels planner rows and estimated heap size separately from an optional observed total size. A zero estimate cannot establish an empty relation. `InspectionGap` identifies the target, schema, object, or migration affected and carries a typed field and reason. Record skipped and truncated structural projections on the snapshot, and record connection, schema visibility, and estimate gaps on the enclosing evidence. An out-of-scope dependency can be reported against the visible object without disclosing the other endpoint. Unsupported object kinds and partition bounds have distinct fields, so they do not imply that a successful table inventory query omitted supported table rows. [Scope and contention probes](research/postgresql-inspection.md#scope-and-useful-fields)

## Structural snapshots and comparison

`SchemaSnapshotV1` covers ordinary and partitioned table identities, columns, indexes, constraints, and scoped partition and dependency edges. Qualified type names on columns are type references, and do not establish a complete inventory for their namespaces. `has_default` records a `pg_attrdef` entry. A generated column uses its generation field to distinguish a generated expression from a column default. An existing expression that could not be read is `unavailable`. A column with no default or generated expression uses `not_applicable`. An index or constraint can retain observed raw properties while its deparsed definition is unavailable.

Constructors and decoders canonicalize independent entries and reject duplicate table names, relation-namespace index names, column names or positions, constraint names within a table, and ambiguous partition pairs. Column attributes sort by physical position, with gaps allowed. Index keys, included columns, and constraint column pairs retain their catalog order. The structural SHA-256 hashes the compact v1 JSON payload of `schema_version`, `schemas`, `tables`, `partition_edges`, and `dependencies` in that order, including field states. Observation time, server version, access and gap metadata, and relation estimates live outside that hash. Scope and projection gaps still govern which additions, removals, and field comparisons can be established. A matching hash cannot establish equivalent coverage.

## Native migration history

`NativeHistoryEvidenceV1` carries a qualified history source when available, its own observation metadata, adapter, coverage, and native events. Complete coverage may contain zero rows. `unavailable` carries no rows and differs from complete empty history. Ranked Flyway events retain installed order, including repeated identities, failures, and superseded runs. Undo events use the Down direction. Goose can retain ranked history when the store exposes a row ID. SQLx and Supabase history entries are unique, unranked forward rows. Skip the Goose bootstrap row.

Native SQLx checksums are SHA-384 and Flyway checksums are signed CRC32 under the supported runner profile. Goose and Supabase provide presence evidence. Use trusted Git or a Guard manifest to compare original bytes in those cases. Plain SQL has no native history source. The optional `native` applied-history basis in an analysis report records the adapter, evidence method, digest of the canonical history artifact, and forward inventory digest. The v1 `manifest` basis keeps its existing shape. [SQLx runner evidence](../fixtures/dmg-02/evidence/README.md) · [Flyway history and checksums](../fixtures/dmg-09/flyway/README.md#discovery-and-history) · [Goose history](../fixtures/dmg-09/goose/README.md#discovery-and-history) · [Supabase history](../fixtures/dmg-09/supabase/README.md#discovery-and-history)

The forward inventory digest binds the adapter and each sorted forward identity, repository path, and Guard SHA-256 of the original bytes. It excludes rollback records and execution metadata. It is an inventory binding and does not authorize a connection or establish freshness. Validate the expected target, inventory, and history coverage before using native evidence in a policy decision.
