# DMG-02 migration fixtures and competitor pilot

The matrices specify proposed fixtures and expected results under the project's analysis and gate contracts. The upstream references record behavior checked on 12 November 2026. Runner, server, Guard, and competitor results are pending. [PLAN.md](../../PLAN.md)

## Fixture inputs and expected decisions

- Give each case a clean Git base and a candidate commit, with a manifest of repository-relative paths, original-byte digests, expected migration identities and directions, target major, runner settings, and policy. Use committed blob bytes for the Git comparison. Preserve fixture bytes on checkout, including the CRLF variant. Compare the two explicit commits, including deletions, and resolve identity changes with the adapter. [Git diff documentation](https://git-scm.com/docs/git-diff)
- **Plain** uses a configured, top-level `migrations/` root, positive integer prefixes, lowercase names with underscores, and numeric order. For runner checks, use `psql` with `-X -v ON_ERROR_STOP=1` and one `--file` invocation per migration. Default to `--single-transaction` and omit it for the declared autocommit and explicit-boundary cases. **SQLx** uses the directory source with CLI and library v0.8.6 as the initial parity pin. Use separate simple and reversible directories. Exercise each applicable adapter on both PostgreSQL 17 and 18. The version table gives separate expectations for those cases. [psql options](https://www.postgresql.org/docs/17/app-psql.html) · [SQLx v0.8.6 CLI](https://github.com/transact-rs/sqlx/blob/v0.8.6/sqlx-cli/README.md)
- Start with `001_base.sql` or `001_base.up.sql` and its Down partner. The base creates the `app` schema, `app.accounts(id bigint PRIMARY KEY, email text, legacy_code text, active boolean)`, and `app.events(id bigint, account_id bigint) PARTITION BY RANGE (id)` with a child covering IDs 1–999. The offline cases use earlier supported SQL to establish schema facts. For server checks, use fresh schema-only and seeded databases. Seed deterministic accounts and matching events, with populated `legacy_code` and non-null `email`. Case overrides specify extra constraints or intentional violations.
- **Safe** is a passing control for the named risk. **Risky** expects the named finding or integrity violation, including warnings that pass. **Incomplete** expects the named required coverage or evidence gap. The proposed fixture `check` policy requires complete coverage and a trusted Git base, denies HIGH and CRITICAL findings, and denies a known content change or removal of a base migration identity. Expected `check` codes are `0` pass, `1` deny, `2` invalid configuration or usage, and `3` required coverage or evidence incomplete. A complete `scan` can return `0` with blocking findings. ## Discovery, integrity, and history

**Source-checked SQLx behavior.** The v0.8.6 directory resolver reads top-level files, parses integer version prefixes on matching filenames, and sorts by numeric version. It derives direction from the suffix. Forward application skips `.down.sql`. The native checksum is SHA-384 over the UTF-8 SQL bytes. PostgreSQL history in `_sqlx_migrations` records version, checksum, and success. The CLI's `migrate run` checks for dirty state, missing versions by default, and checksum mismatches on forward migrations. Pair validation and ambiguous-identity diagnostics below are proposed Guard behavior. ## Risk, execution, and coverage

**Source-checked PostgreSQL behavior.** A nullable column add and a column add with a constant default avoid a table rewrite. A volatile default such as `clock_timestamp()` rewrites the table. `ALTER TABLE` generally takes `ACCESS EXCLUSIVE` and uses the strongest required lock across combined subcommands. `SET NOT NULL` ordinarily scans existing rows and can skip that scan when a retained, validated check proves non-nullness. A separate `VALIDATE CONSTRAINT` step scans previously unvalidated data under `SHARE UPDATE EXCLUSIVE`. [PostgreSQL 17 ALTER TABLE](https://www.postgresql.org/docs/17/sql-altertable.html) · [PostgreSQL 18 ALTER TABLE](https://www.postgresql.org/docs/18/sql-altertable.html)

### Transaction handling and source spans

**Source-checked execution.** SQLx v0.8.6 tests for `-- no-transaction` at the beginning of the file. By default, the PostgreSQL runner wraps the script and essential history write in a transaction. With the opt-out, it sends the script as a single simple Query message. PostgreSQL executes multiple statements in one such message in an implicit block unless there are explicit transaction boundaries. The resulting prediction for T04 is a server rejection of the concurrent index build. Verify it on both pinned servers. [SQLx directive](https://github.com/transact-rs/sqlx/blob/v0.8.6/sqlx-core/src/migrate/source.rs#L106-L125) · [SQLx script execution](https://github.com/transact-rs/sqlx/blob/v0.8.6/sqlx-postgres/src/migrate.rs#L190-L272) · [SQLx executor](https://github.com/transact-rs/sqlx/blob/v0.8.6/sqlx-postgres/src/connection/executor.rs#L253-L265) · [PostgreSQL message flow](https://www.postgresql.org/docs/18/protocol-flow.html) · [Concurrent index restrictions](https://www.postgresql.org/docs/18/sql-createindex.html#SQL-CREATEINDEX-CONCURRENTLY)

### Version-sensitive DDL

PostgreSQL 18 permits named `NOT NULL` constraints with deferred validation and `NOT VALID` foreign keys on partitioned tables. PostgreSQL 17 documents `NOT VALID` for ordinary CHECK and foreign key constraints and explicitly excludes the partitioned foreign key case. Use the same bytes on both majors. V01 exercises grammar or syntax coverage and V02 exercises a version-specific restriction on a recognizable operation. [PostgreSQL 18 release notes](https://www.postgresql.org/docs/18/release-18.html) · [PostgreSQL 18 regression SQL](https://github.com/postgres/postgres/blob/REL_18_STABLE/src/test/regress/sql/alter_table.sql) · [PostgreSQL 17 ALTER TABLE](https://www.postgresql.org/docs/17/sql-altertable.html)

## Independent holdout review

1. Use the published cases for development and preflight. Have a reviewer outside rule development select additional synthetic or approved sanitized cases from actual migration patterns. Sample by rule family, adapter and major, and include matched risky and safe controls plus ambiguous and unsupported inputs. Cover each blocking rule and destructive forms such as table drop, column drop, and truncate. Group a migration with its revisions, dialect-neutral copies, and cosmetic variants in one split. Use both adapters and both majors in the holdout itself.
2. Have a PostgreSQL reviewer and an adapter or QA reviewer independently label the cases before seeing tool output. Record the original statement span and object, baseline and runner evidence, expected risk and severity, expected coverage and gate, and supporting documentation or disposable server observations. Resolve disagreements with a native runner or two-session probe when applicable. Record any remaining ambiguity as a coverage expectation with a reason.
3. Freeze the reviewed manifests, case bytes, and labels by commit and digest before rule tuning. Keep holdout inputs and labels with the independent reviewers through candidate selection. Score the candidate against that frozen set. Log any correction to the corpus and rerun the whole set. Move exposed cases to regression coverage and replenish the holdout before the next tuning cycle.
4. For release, require each in-scope destructive holdout case to produce the corresponding finding or a blocking incomplete result tied to the relevant coverage gap. Count confirmed findings, missed risks, false positives, and unsupported or incomplete cases by rule, adapter, and major. Report a blocking incomplete result as a gate outcome and a coverage gap.
