# PostgreSQL catalog inspection feasibility

On 13 November 2026 the [native probe](../../fixtures/dmg-10/catalog/native_probe.py) checked PostgreSQL 15.20, 16.16, 17.12, and 18.7 on x86-64 Ubuntu 24.04.4 under WSL2 in isolated network and IPC namespaces. Each run created and stopped its own cluster. The restricted login had `CONNECT` on one database and effective `USAGE` on the authorized schemas. It held no application table grants, schema `CREATE`, ownership, elevated role attributes, or `pg_read_all_stats` membership. `SELECT` of an application column returned `42501`. `CREATE TABLE` inside the inspection transaction returned `25006`. [Privileges](https://www.postgresql.org/docs/18/ddl-priv.html) · [Predefined roles](https://www.postgresql.org/docs/18/predefined-roles.html) · [Read-only transactions](https://www.postgresql.org/docs/18/sql-set-transaction.html)

## Scope and useful fields

Join a bound list of explicitly authorized, non-system schema names to `pg_namespace`. Check `has_schema_privilege(n.oid, 'USAGE')` against the effective reader role before traversing the schema. The probe distinguished an existing allowed empty schema, a denied schema, and a missing schema. Inherited and `PUBLIC` grants made a schema visible, and the owner control had effective `USAGE` and `CREATE`. Raw `pg_namespace` still exposed the denied schema. The inspector's scope filter limits its output, while PostgreSQL catalog ACLs govern what the login itself can query. A denied or unavailable schema cannot supply absence evidence for its objects. [Schema privileges](https://www.postgresql.org/docs/18/ddl-schemas.html#DDL-SCHEMAS-PRIV) · [Privilege inquiry functions](https://www.postgresql.org/docs/18/functions-info.html#FUNCTIONS-INFO-ACCESS-TABLE)

| Evidence | Projection and bounds |
| --- | --- |
| Tables and partitions | Read `pg_class` and `pg_namespace` for ordinary and partitioned tables. Use `pg_inherits` for parent edges and the detach-pending flag. Retain both endpoints when in scope and mark an omitted endpoint as outside the observed scope. |
| Columns and types | Use positive `pg_attribute.attnum` with dropped columns excluded. Keep column identity, position, type identity and modifiers, default presence, nullability, and identity or generated state where supported. Read default expression definitions as a separate optional field. |
| Indexes and constraints | Record index readiness and validity independently. Use typed constraint kinds, columns, reference edges, and validation and enforcement fields. Record PG18 `pg_constraint.conenforced` and `contype = 'n'` with a separate fixed query projection. PostgreSQL 15–17 represent column nullability through `pg_attribute.attnotnull`. Use the constraint's own validation state for a named NOT NULL on 18. |
| Planner estimates | Record finite nonnegative `pg_class.reltuples` as a planner row estimate. `-1` means unknown. Multiply `relpages` by the server's `block_size` for a heap estimate. Prefer unknown for a zero-page result with unknown row statistics. Leave partition-parent aggregate size unavailable until its complete partition scope is known. |

The analyzed fixture had 256 estimated rows, a 16,384-byte estimated heap, and a 73,728-byte observed total including indexes and TOAST. The never-analyzed table had unknown row count. Treat each value as an observation about the sampled environment. Planner values can lag writes, and catalog size estimates cannot establish that a relation is empty. The parent table's heap estimate was inapplicable. [pg_class](https://www.postgresql.org/docs/18/catalog-pg-class.html) · [pg_attribute](https://www.postgresql.org/docs/15/catalog-pg-attribute.html) · [pg_inherits](https://www.postgresql.org/docs/18/catalog-pg-inherits.html) · [PostgreSQL 17 constraints](https://www.postgresql.org/docs/17/catalog-pg-constraint.html) · [PostgreSQL 18 constraints](https://www.postgresql.org/docs/18/catalog-pg-constraint.html)

## Contention and partial evidence

A separate session held `ACCESS EXCLUSIVE` on the populated table. Scope, relation estimates, partition edges, and raw column, index, and constraint catalog fields completed on every major. With the same scope, `pg_get_expr`, `pg_get_indexdef`, `pg_get_constraintdef`, and `pg_total_relation_size` waited and returned `55P03` under the 100 ms lock limit. A 50 ms statement timeout and 1 s lock limit returned `57014`. Revoking `PUBLIC` execution on the size function returned `42501` and left planner estimates readable. The probe recovered the read-only transaction with `ROLLBACK TO SAVEPOINT` after each error. Its short local samples include process startup and are useful for reproducing the lock distinction. Larger catalogs and production contention require separate performance measurements. [System information functions](https://www.postgresql.org/docs/18/functions-info.html#FUNCTIONS-INFO-CATALOG-TABLE) · [Object size functions](https://www.postgresql.org/docs/18/functions-admin.html#FUNCTIONS-ADMIN-DBSIZE) · [Timeouts](https://www.postgresql.org/docs/18/runtime-config-client.html#RUNTIME-CONFIG-CLIENT-STATEMENT) · [SQLSTATE](https://www.postgresql.org/docs/18/errcodes-appendix.html)

Use one short `REPEATABLE READ READ ONLY` transaction for the structural snapshot. Set a safe local search path and transaction-local statement, lock, and idle limits. Apply an outer monotonic deadline to DNS, TCP, TLS, queries, and cleanup. Run fixed parameterized projections with explicit schema scope, deterministic ordering, and an extra row beyond each configured limit to detect truncation. Bound accepted field and payload bytes. PostgreSQL can still scan or sort catalog rows before producing the first bounded result, so keep server and client deadlines active. Collect raw structural fields first. Put optional deparsing or size reads behind savepoints, roll back an optional failure, and retain successful observations. Roll back and close the connection on deadline or unexpected errors. Any optional `pg_locks` sampling should use the current database and the observed relation scope, emit only relation and mode summaries, and identify the results as a separate volatile observation. [Transaction snapshots](https://www.postgresql.org/docs/18/transaction-iso.html) · [pg_locks](https://www.postgresql.org/docs/18/view-pg-locks.html)

## Transport and evidence contract

The PostgreSQL 18.7 TLS run used a fixture CA, a leaf certificate with a `localhost` DNS SAN, and a loopback `hostssl` rule with SCRAM. The native libpq client succeeded with `verify-full` and the matching CA and name. It rejected a different host name and an untrusted CA, and the fixture server rejected plaintext. The proposed Rust implementation uses `tokio-postgres` with `SslMode::Require`, plus `tokio-postgres-rustls` and a standard rustls verifier configured with the authorized CA roots and exact endpoint name. Require an explicit protected target configuration and reject unsupported SSL modes or endpoint overrides. Wrap connection setup and the transaction in an outer timeout, with no fallback to plaintext for TCP. This probe verified the server and libpq behavior. The Rust connector still needs its own four transport checks. [PostgreSQL certificate validation](https://www.postgresql.org/docs/18/libpq-ssl.html) · [Driver TLS modes](https://docs.rs/tokio-postgres/latest/tokio_postgres/config/enum.SslMode.html) · [Rustls connector](https://docs.rs/tokio-postgres-rustls/0.14.0/tokio_postgres_rustls/struct.MakeRustlsConnect.html) · [Rustls client verification](https://docs.rs/rustls/0.23.46/rustls/struct.ConfigBuilder.html)

The [v1 inspection evidence contract](../inspection-evidence.md) defines the shared types. The proposed wire fields below summarize the transport and scope requirements.

- `InspectionEvidenceV1` carries `schema_version`, an `observation` with `target_id`, `server_version_num`, and `observed_at_unix_seconds`, explicit `scope`, optional `snapshot` and `history`, and typed gaps. `target_id` is the caller's opaque authorized environment identifier. Keep server host, port, database, and role in the protected connection input. Capture UTC time for freshness and keep observation metadata outside the deterministic structural digest.
- `scope` records requested schemas with `visible`, `denied`, `missing`, or `unavailable` and any reached limits. Per-field evidence can be `observed`, `estimated`, `unavailable`, or `not_applicable`. A requested missing schema differs from a visible empty schema. Retain partial rows and typed reason codes for insufficient privilege, unsupported projection, contention, query cancellation, deadline, and truncation. A `57014` result only establishes cancellation unless its cause is verified.
- `SchemaSnapshotV1` uses qualified typed names compatible with `DatabaseObject`, plus typed column, index, constraint, and dependency data. OIDs join records during collection. Canonicalize order and hash the structural payload independently from row estimates, runtime timings, and permission or observation metadata. Keep deparsed definitions in a protected snapshot as potentially sensitive values. Routine findings and logs use safe identity, scope, reason, and SQLSTATE only. Exclude DSNs, credentials, query text, application row data, and raw server messages.
- `NativeHistoryEvidence` has its own selected adapter, qualified source, observed coverage, native identity and checksum fields, and binding to the relevant original-byte inventory. A separate history connection needs its own observation time and scope. Share snapshot provenance only when collected in the same transaction. Grant `USAGE` and narrow `SELECT` on the designated history source separately from structural inspection. Treat a failed or unavailable history read as unknown, and preserve the runner's checksum semantics separately from Guard's raw file SHA-256.

## Reproduction

Run with Python 3.11 or later as a regular Unix user. Substitute each pinned PostgreSQL binary directory in turn. For the optional TLS run use an OpenSSL-enabled server and client and an installed `openssl`. Ordinary probes use only the temporary Unix socket. The TLS probe uses loopback and a generated certificate. The JSON records contain executable digests and the observed fields and SQLSTATEs. Timing varies between runs.

```sh
python3 -B fixtures/dmg-10/catalog/native_probe.py --pg-bin /path/to/postgresql-15.20/bin
python3 -B fixtures/dmg-10/catalog/native_probe.py --pg-bin /path/to/postgresql-18.7-tls/bin --tls
```
