Each SBOM additionally identifies seven Guard workspace libraries and the Guard CLI application. The Windows and Linux counts overlap. `errno` 0.3.15 and `libc` 0.2.191 are target sources on Linux and host-only on Windows. All 180 unique registry archives matched the checksums in the committed Cargo.lock, whose SHA-256 is `aa374723aa1e78466cc54a42bf63195e7e66790aa843495d6e8263f6895b4221`. The staged Windows archive used CRLF, which changes its lockfile digest without changing the pinned package records. [SBOM scope and staging](../release.md#sbom-and-notices)

The local draft contains a per-package CSV and JSON inventory with version, archive SHA-256, declared license expression, per-target build role, and collected notice paths. Registry material includes 293 notice files for target sources and 87 for packages compiled only on the host. The exact crates supply the standalone files for 179 registry packages. `pg_query` 18.1.0 supplies its license declaration and vendored source headers. The draft retrieves the missing standalone notices from pinned upstream source and retains the shipped source headers as separate text extracts. The SBOM records compiled sources and identifies its composition as incomplete. Optimized binary content, generated code, the Rust runtime, and system libraries require separate review. ## Normalized Windows and native Linux review bundle

The local `dmg-native-notice-review.zip` pairs the normalized Windows package from `2d3e5e0` with the native Linux package from `af21401`. The Windows executable, SBOM and manifest SHA-256 values are `4f318dfaf46678a716e8a66a6e03b8f833ed14b2cc3bf3946bfb01fe8e7d576d`, `01336c048c0babfe234a1ce12d8949c1feadf08bc56f6fb9f1ca2dda037fda07` and `eb875e3be11e1504d683849ff19def662c6658c7a377c7b2937db82c95f6c619`, respectively. Both packages passed manifest and checksum verification. Their normalized lockfile and toolchain hashes match their committed Git blobs, and both SBOMs match the previous review's registry package roles and six vendored component records for license and build role. [Normalized Windows staging](integrated-windows-verification.md) · [Native Linux staging](integrated-linux-verification.md)

The bundle rechecks all 180 crate archive hashes and the 380 notice files taken from those archives. It retains 412 notice files in total and adds a record of the two target builds' generated inputs. The record pairs each of ring's 12 x86-64 assembly selections with its generator, packaged Linux assembly, and Windows assembly and preassembled object. It retains the verbatim notice headers of the generators and the translator. It also pins the pg_query parser, scanners and protobuf inputs. The native staging helper sets `DOCS_RS=1` so the pg_query build uses the packaged Rust protobuf definitions. These are records of build inputs. The final notice review still needs to consider the optimized binaries and any additional runtime files shipped with them. [Native staging helper](../../scripts/stage-release.py)

Two independent assembly runs produced the same ZIP SHA-256, `692f8fd058e821e9024269bd6ae45eca5a90b72e14fc7a021375b35702545653`. Use the bundle's per-file checksums and package pins before review. The project license decision and approval of the final notice set remain with the release owner. A macOS package needs its own inventory and runtime review.
